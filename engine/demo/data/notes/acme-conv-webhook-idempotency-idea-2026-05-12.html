Webhook Idempotency ? Processed Events Table

Idea: we should add idempotency handling to the Stripe webhook processor in src/payments/webhooks.ts to prevent double-processing of events when Stripe retries failed deliveries. Stripe can retry a webhook event up to 72 hours after the first attempt.

Implemented a processed_webhook_events table approach: before processing any event, we INSERT the event ID into the table. If the event is already recorded, we return 200 immediately and skip business logic. This is more reliable than checking for side-effects because some operations (like creating a payment record) are not idempotent by nature.

We should also improve the error recovery path: currently, if business logic throws after recording the event, the event is marked failed but never retried internally. Should add a dead-letter queue or manual retry mechanism for failed webhook events.
