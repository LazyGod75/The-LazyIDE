Refresh Token Storage ? Switched to Hashed Storage After Security Review

Fixed a security issue discovered in the session management code in src/auth/session.ts. The original design stored refresh tokens in plaintext in the sessions table. A security review identified this as a problem: if the sessions table is leaked via SQL injection or backup exposure, all refresh tokens would be immediately usable by an attacker.

We decided to store only a SHA-256 hash of the refresh token. On validation, we recompute the hash of the incoming token and compare. Production should upgrade this to bcrypt with a cost factor of 10 or higher since SHA-256 is fast enough to brute-force with GPU acceleration.

Refresh token rotation was also added: when a refresh token is used, the old session is revoked immediately and a new session is created atomically. This prevents refresh token replay attacks ? if an attacker steals a refresh token and uses it, the legitimate user's next refresh attempt will fail and trigger a security alert.
