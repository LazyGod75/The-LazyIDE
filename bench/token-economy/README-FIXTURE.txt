TOKEN-ECONOMY BENCHMARK — design notes, reproduction, known limitations
=========================================================================

Goal: measure tokens-injected-per-correctly-answered-question across
retrieval configurations, so a "LazyBrain uses fewer tokens" claim can be
supported (or refuted) with evidence. See scratch/_brain-sota-research.md
in this repo for the prior-art framing (TERAG, HtmlRAG, arXiv 2601.00821
"verbatim beats extracted") this design responds to — NOTE: that file did
not exist in this repo at the time this harness was built; the framing
below is derived from the task brief that quoted it, not from reading the
file directly.

WHAT'S HELD FIXED
  - questions.json: 24 questions with verifiable ground truth, drawn from
    this repo's own git history (commit hashes cited) or from code read
    directly (cited as "HEAD"). Never generated by reading the brain first.
  - Answering model: Claude Haiku via the `claude -p` CLI (same invocation
    shape as src/cli/lib/agentLoop.ts's claudeCall), --disallowedTools
    blocking every built-in tool. This is load-bearing: without
    --disallowedTools, haiku will just go Read the real file off disk
    instead of using the injected context, silently making every config
    "win" — caught during pilot development, see git history of
    lib/answerModel.mjs.
  - Prompt template: lib/answerModel.mjs's PROMPT_TEMPLATE, identical
    across every config.

WHAT VARIES: the four retrieval configurations
  (a) flat_rag       — lib/configs/flatRag.mjs. Fixed-line chunks (60
      lines, 10 overlap) of the raw corpus, ranked by keyword/substring
      overlap with the question, greedily packed into a token budget. Two
      budgets run (800, 3000) to get two points on the accuracy/tokens
      curve — small vs large budget is exactly the axis HtmlRAG's result
      turns on.
  (b) lazy_targeted  — lib/configs/lazyTargeted.mjs. skeleton = the
      directory's file list (the codebase's own layout, ~1 line/file).
      leaf = ONLY the one matching attribute: the target symbol's
      file-neuron anchor heading (function/class signature) when the
      question names a real AST symbol, else the file's one-line TLDR.
  (c) lazy_full_subtree — lib/configs/lazyFullSubtree.mjs. Same skeleton as
      (b), but instead of the one filtered leaf, dumps the FULL stripped
      file-neuron content for EVERY file in that directory. This is the
      control that isolates "does the hierarchy help" (shared with b) from
      "does attribute filtering help" (only b has it).
  (d) grep_read      — lib/configs/grepRead.mjs. Extracts identifier-like
      terms from the question text, greps the corpus, reads the top-hit
      files WHOLE (verbatim), budget-truncated. Two budgets (1500, 6000).

Every config reads from the SAME corpusDirs (questions.json.corpusDirs) —
the LazyBrain fixture brain was code-scanned from exactly these
directories, nothing more, nothing less.

THE LAZYBRAIN FIXTURE BRAIN
  Built by the REAL production CLI (`lazybrain graph --cwd <dir>`, i.e.
  the actual code-scanner + file-neuron composer — engine/src/graph/
  code-scanner.ts, engine/src/annotator/blocks/composers/file-neuron.ts),
  once per corpusDir, into an ISOLATED directory (LAZYBRAIN_FIXTURE_BRAIN),
  never David's real brain. Reproduce with:

    cd engine && npm run build          # if dist/ is stale
    node scripts/build-fixture-brain.mjs <someIsolatedDir>

  lib/lazyFixture.mjs then reads the generated note HTML directly (regex
  extraction of specific sections/anchors) rather than shelling out to
  `lazybrain query`/`search` per lookup — verified by hand that
  `lazybrain query "#fn-picklevel" --strip` returns byte-identical text to
  what extractSymbolAnchorText() extracts. The CONTENT is 100% the real
  pipeline's output; only the "give me node X's text" step is inlined for
  speed (would be ~50 extra CLI spawns for a 24-question x 2-config run).

  Indexing cost (results/fixture-build-report.json): 173 files across 7
  directories, 102.7s wall time, 0 LLM calls, $0. This is the number to
  set against GraphRAG's ~$33k-of-LLM-calls-per-5GB-corpus figure — the
  brain's structure comes from AST parsing, not extraction calls. That is
  LazyBrain's actual, checkable defence for the amortisation argument.

CORRECTNESS GRADING
  Primary (and, in this pilot, only) grader: lib/grader.mjs's
  gradeKeywordMatch — ground truths were deliberately written as specific
  identifiers/numbers so "does the answer contain every required term" is
  a legitimate exact-match proxy. An LLM-judge path (gradeLlmJudge, 3-run
  majority vote against a fixed rubric) is implemented but NOT exercised
  in the bundled pilot — time-boxed. Turn it on for a fuller run via
  run.mjs (not yet wired to a CLI flag — call lib/grader.mjs directly, or
  extend run.mjs's grading branch).

PILOT RESULTS (bundled: results/raw/, results/summary.json,
results/pilot-2026-08-16-meta.json)
  6 of 24 questions x 6 config-variants = 36 calls (q01, q03, q06, q10,
  q13, q20 — 3 structural, 3 behavioral, spanning 4 of the 6 corpus dirs).
  See the top-level task response for the actual numbers and what they
  mean; this file only documents the mechanism.

KNOWN LIMITATIONS (found DURING the pilot — not smoothed over)
  1. File-neurons in this repo's current dogfood state are SIGNATURE-ONLY
     (renderFunctionAnchor/renderClassAnchor emit a heading, never a body —
     see file-neuron.ts). No conversational enrichment (decisions/bugs
     attached from commit messages or chat) was captured for this fixture
     — that pipeline exists (conv-file-enrichment.ts) but needs
     conversation transcripts this harness does not have. So configs (b)
     and (c) are structurally incapable of answering questions whose
     ground truth lives in a function BODY rather than its signature. This
     is real, not a harness bug — it is exactly the gap arXiv 2601
     ("verbatim beats extracted") predicts, and exactly why questions.json
     deliberately includes both "structural" (signature-answerable) and
     "behavioral" (body-answerable) categories.
  2. Some ground-truth facts (e.g. q03's "edge count went 0 -> 1658") come
     from the git COMMIT MESSAGE, not from any text present in the current
     source files. No config here reads git history, so that specific
     number is unwinnable by every config equally — a fair-but-blunt
     grading edge, not a bug. A fuller run should either add commit
     messages to the corpus (which conv-file-enrichment.ts's real pipeline
     effectively does via captured conversations) or relax those specific
     required-terms to code-only facts.
  3. Naive grep-by-hit-count can rank a test file (many literal calls to
     the function under test) above the implementation file. Left as-is —
     it is a real, honest property of a naive grep+read baseline, not
     patched to make config (d) look better.
  4. estimateTokenCount() (lib/tokenize.mjs) is a heuristic (0.25-0.33
     tokens/char), not real BPE — deliberately kept identical to
     engine/src/util/tokenize.ts's estimator so this harness's numbers are
     comparable to LazyBrain's own existing "1.7x fewer tokens" figure,
     which uses the same estimator. Real usage.input_tokens from each
     `claude -p` call is also recorded per-record (results/raw/*.json) as
     an audit cross-check, though it reflects the whole prompt (context +
     question + template), not injected-context tokens alone.

COST/TIME FOR A FULL 24-QUESTION x 6-VARIANT RUN (144 calls)
  Pilot: 36 calls, wall time ~9 minutes end to end (indexing excluded,
  already built). Linear extrapolation: ~36 minutes for all 24 questions x
  6 variants. Answering model is Haiku on the Claude subscription (no
  incremental $ cost reported by David's own account setup) — `claude -p
  --output-format json` does report a total_cost_usd per call (~$0.01-0.03
  observed with cache creation), which is an internal API-equivalent cost
  estimate, not an actual charge against a subscription plan.
